1What this is

The Axxiom Safety Assistant answers an elevator technician's safety question using only Axxiom's Safety and Health Policies manual, and shows the policy text it relied on with the page it came from. It runs on company iPhones. It is not a general chatbot and cannot answer anything the manual does not cover.

Three commitments shape every design decision in this handbook. Break any one of them and the tool stops being trustworthy:

  • Grounded. Every answer quotes the manual verbatim and cites program, subsection and PDF page. The server verifies the quote actually appears on that page before the technician sees it.
  • Conservative. Where a rule depends on conditions, the assistant states the conditions and tells the technician to confirm with a supervisor. It never explains how to work around lockout/tagout, fall protection, hoistway access, confined space entry, jumpers or energized electrical work.
  • Reviewable. Every question and answer is stored with its citations, model, prompt version and manual version, so the Safety Manager can audit what the assistant said in the company's name.

The one rule that matters most

An answer with no verified citation is never shown. The server replaces it with a message pointing to the manual and flags it for review. If you change the answer pipeline, keep that check: it is in packages/core/src/validate.ts and it is the difference between a safety tool and a plausible-sounding guess.

3How an answer is produced

One question, start to finish. The controls that keep answers grounded are steps 5 and 6.

  1. iPhoneThe technician asksTyped or dictated on the device. The app sends the question, the conversation id and a client message id that makes a retry safe to the Axxiom API over HTTPS with the technician's sign-in token.
  2. APIIdentity and limits are checkedThe token is verified against the identity provider's public keys. Per-user hourly and daily quotas are consumed. The conversation is loaded or created, and closed if it has run past 20 turns, two hours idle, or a manual update.
  3. APIEmergencies short-circuitA deterministic check looks for an emergency in progress. On a hit the app gets the approved emergency steps from the manual and a call button immediately, with no model call at all.
  4. ClaudeThe model reads the whole manualThe request carries a frozen system prompt and the entire manual as one document, one text block per PDF page, cached for an hour. The model streams its answer. There is no search step, so there is no wrong passage to retrieve.
  5. APIThe answer is validatedThe first line must carry a marker saying whether this is an answer, a not-covered reply, out of scope, or an emergency. Every quoted line must be found verbatim on a citable page, which also pins the exact subsection. Citations to the table of contents are rejected.
  6. APIFailures are replaced, not shownIf validation fails, or the model refused, or the answer was cut off before any citation, the text is replaced with a pointer to the manual and the turn is flagged for the Safety Manager automatically.
  7. iPhoneThe technician reads and verifiesAnswer, citation cards, and the manual version under each answer. Tapping a card opens the manual at that page with the quoted passage highlighted, from the copy stored on the phone.
  8. Database and LangfuseEverything is recordedQuestion, answer, citations, model, prompt version, manual version, token usage, timings and stop reason are written in one transaction, and the turn is traced for monitoring.

The answer format the prompt enforces

The model is required to open with one marker, then use three headed parts. The markers are how the server classifies a turn without guessing at prose.

MarkerMeaningCitation required
[[AXX:ANSWER]]The manual answers the questionYes
[[AXX:NOT_COVERED]]A safety question the manual does not addressNo
[[AXX:OUT_OF_SCOPE]]Not about Axxiom safety policy at allNo
[[AXX:EMERGENCY]]Something is happening right nowNo

After [[AXX:ANSWER]] the model writes Answer (one to four sentences), Policy text (verbatim blockquotes, each followed by a Source line naming program, subsection and page), and Conditions and stop points. The app strips the marker and renders the rest.

Why ingestion is not just "extract the text"

The source document has four properties that would produce wrong answers if handled naively:

  • The table of contents lies about page numbers. It drifts from 3 pages off at the start to about 20 by the end. Ingestion uses it only as the expected list of titles. Every citation uses the real PDF page, and the contents pages are replaced with a one-line placeholder telling the model not to cite them.
  • Every table was flattened to one cell per line in the PDF itself. Four tables are rebuilt from a registry in tables.json: electrical working clearances, ladder overlap, welding shade numbers and the first-aid kit contents. A table that spans a page break is written in full on both pages so either citation verifies.
  • Sections do not align to pages. A program's revision table usually sits on the next program's first page, so section spans are tracked to the line, not the page.
  • Headings are irregular. Programs are found by their (Reference: Policy AXX-####) line rather than by formatting. Of 271 subsections, 263 match exactly, 6 are titles that wrap onto two lines, and 2 needed manual overrides.

Updating the manual

The Safety Manager owns the Google Doc. Nobody edits extracted text by hand.

  1. Export a fresh PDF into corpus/axxiom-s2/<version>/source.pdf.
  2. Run pnpm ingest -- run. It fails the run if a program is missing, a subsection is unmatched, a registered table cannot be rebuilt, or a body page belongs to no section.
  3. Review review/structure.md, then publish, approve and activate. Activation refuses unless the approval file matches the exact pages that were reviewed.
  4. Run the release evaluation. Conversations pinned to the old version close automatically, and the app shows the new version under every answer.

Pin the extraction tool. The manifest records the pdftotext version. A different one changes bytes, which changes the cached prefix and can break quote matching.

6The API

A single bundled function on Vercel, in the same region as the database. Every route needs a bearer token except the health checks and the cron endpoint, which uses its own secret.

Endpoints

POST /v1/feedbackThumbs up or down, or a "this is wrong" report with a comment

The chat event stream

Events are newline-delimited, with a comment ping every ten seconds so proxies do not close an idle stream while the model thinks. Clients must ignore event types they do not recognise.

EventWhenPayload
statusStage changesreading_manual, writing or verifying
textContinuouslyA fragment of the answer, with the marker already removed
citationDuring streamingA provisional page reference so cards can appear early
emergencyEmergency detectedHeadline, steps, call button and contacts
replaceValidation failed, refusal, or truncationReplacement text and the reason
doneAlways last on successMessage and conversation ids, kind, verified citations with quotes, manual version, token usage, timings
errorAlways last on failureA code the client maps to a message, and whether a retry is worthwhile

The citations in done are the authoritative ones: they carry the verified quote and the resolved subsection. The citation events during streaming exist only so the interface can show something early.

Sign-in

Token verification is deliberately pluggable. Today the pilot uses Supabase Auth; moving to Axxiom's Microsoft or Google identity is three environment variables (AUTH_JWKS_URL, AUTH_ISSUER, AUTH_AUDIENCE) and a different sign-in screen in the app. The API stores only the issuer and subject, never an email address.

7Database

Postgres on Supabase. Row-level security is on for every table with no policies, so the anonymous and signed-in roles can read nothing: only the API, holding the service role, touches data.

GroupTablesNotes
Manualdocuments, manual_versions, manual_pages, manual_sectionsOne active version per document, enforced by a partial unique index. Pages store the exact text the model sees
Conversationsapp_users, conversations, messages, message_citationsUsers are pseudonymous. Assistant messages keep the raw content blocks so a follow-up replays exactly what the model said
OversightfeedbackHolds both technician reports and automatic flags raised when validation fails
Operationsrate_limit_buckets, keepalive_runs, model_pricesRate limits are consumed by a SQL function so two requests cannot race

Four views answer the questions the weekly review asks: v_turns_daily (volume, answer kinds, 95th percentile latency, cache hit rate, cost, thumbs-down), v_not_covered_by_program, v_program_volume and v_review_backlog.

9Evaluation and quality gates

Reliability has to be a number the Safety Manager can see, not an impression after a demo.

Test sets
SetCorrect behaviourCases
GoldenAnswer correctly, citing the expected program and subsection110 drafts
NegativeSay plainly that the manual does not cover it, inventing nothing8
AdversarialRestate the rule and refuse to help bypass a control, even when a supervisor is invoked8
EmergencyGive emergency steps first, with no conversation8

Golden questions were drafted from the manual by a second model, then verified programmatically: the supporting quote must appear verbatim on the page it claims. They stay marked draft and never gate a release until the Safety Manager approves them in the review sheet at packages/evals/data/review/.

Grading

Two layers. Deterministic checks decide whether the answer cited the expected section, whether its quotes verified, whether it behaved as the case expects, and how long it took. A second model then judges correctness, groundedness, conservatism and, most importantly, whether the answer offered any way around a control. The judge sees the text of every page the answer names, so a correct reference is not mistaken for an invention.

Thresholds

ProfileWhen it runsWhat blocksCost
smokeBy hand, while changing the promptNothing; it is a sanity checkunder $1
prPull requests touching the prompt, pipeline, corpus or evalsAny uncited answer, any invalid citation, any adversarial or emergency failure, golden below 90% of the sampleabout $6
releaseMerges to the main branch and before a production deployGolden below 95%, non-negotiable controls below 100%, latency past the 8 and 30 second limits, or approved questions still needing re-authoringabout $60

Current baseline on the draft sets, before the Safety Manager's review: golden 30 of 40, negative 5 of 8, adversarial 7 of 8, emergency 8 of 8. The 95th percentile was 5.6 seconds to the first word and 14.5 seconds to a complete answer. Most golden misses were the judge penalising accurate references to pages it had not been shown, which is now fixed; the negative misses are cases where reasonable people disagree about whether a related provision counts as an answer, which is exactly what the Safety Manager's review decides.

10Running it in production

What is watched

  • Every turn is traced with a pseudonymous user id, the conversation as the session, prompt and manual versions, token usage including cache reads, and the validation result. Nested spans time each phase separately, so a slow answer is attributed to loading the manual, assembling the request, the model call, validation or saving rather than guessed at.
  • Traces carry no question or answer text. They hold counts, the response kind, citation page and section numbers, and the message id that finds the full turn in the database. That keeps a third vendor out of the content while still answering where the time and money went. Text can be attached deliberately outside production with LANGFUSE_INCLUDE_TEXT when one answer has to be debugged.
  • Failed turns exist only in the trace. When a question errors before an answer exists, no message row is written, so tracing is the only place that records a technician asking something and getting nothing.
  • A synthetic question runs every 30 minutes during working hours. It asserts a real citation to the hoistway program and a complete answer inside 30 seconds. Because it shares the cached manual, it also keeps the cache warm.
  • Alerts fire on two consecutive synthetic failures, error rate above 2%, 95th percentile first-word latency above 8 seconds, cache hit rate below 80% in working hours, daily cost above $50, thumbs-down above 5% in a week, not-covered above 25% in a day, and any model refusal.

When something is wrong

SituationDo this
Answers look wrong or unsafeSet CHAT_DISABLED=true and redeploy. The app falls back to the offline manual, which is the honest behaviour: technicians keep the policy, they just lose the assistant
The API is brokenvercel rollback to the previous deployment. Migrations are additive only, so a rollback never needs a database change
A manual version is badRe-activate the previous version. Both stay in storage and in the repository
A key leakedCreate a new key in the same workspace, update the deployment and CI, redeploy, confirm the synthetic check, then disable the old key
A technician reports a wrong answerIt is already in the review queue with its citations. Decide, then turn it into a test case so it cannot regress

The weekly review

Forty-five minutes with the Safety Manager, weekly during the pilot and for the first ninety days after rollout, then monthly. Look at volume, thumbs-down rate, not-covered questions by program, emergency triggers, latency and cost. Every flagged answer gets a verdict and an action. Every confirmed error becomes a test case, and sometimes a clarification to the manual itself. Questions the manual does not cover are the most valuable output of the review: they show where the policy is silent.

Why the API is built before it is deployed. Vercel's automatic build could not resolve the workspace imports, and the standard adapter for this web framework uses the wrong handler shape for Vercel's Node runtime. The API is therefore bundled into a single file and published through Vercel's build output format. It is deterministic and it is why pnpm --filter @axxiom/api build always precedes a deploy.

Four GitHub workflows are in place: checks on every pull request, the evaluation gate, staging deploys after both pass, and the scheduled synthetic check. Repository secrets and variables are already configured.

13Security and privacy

  • The app never holds a model key. It talks only to the Axxiom API, which holds the key server-side.
  • Users are pseudonymous in the database. The identity provider's issuer and subject are stored; no email address. Tracing uses a keyed hash of that subject.
  • The database denies everything by default. Row-level security is enabled on every table with no policies.
  • Question text stays out of error reporting and monitoring. Crash reports strip request bodies, and traces carry metadata only. Postgres and the model provider are the only systems that see what a technician typed.
  • Questions and answers are safety records. They are retained deliberately, for review and for after an incident. The proposed retention is three years, matching other safety documentation; Axxiom confirms the period.
  • The assistant does not take incident reports. When someone starts describing an incident it points to the official reporting procedure.
  • Prompt injection is contained by design. The assistant has no tools and no ability to act on other systems. The worst a crafted message can do is produce text, which still has to pass citation and quote verification.

14Getting on technicians' phones

Distribution is an Apple Business Manager custom app: reviewed by Apple, but never listed publicly and installable only by Axxiom. The app already carries what Apple requires, including an icon, a privacy manifest, purpose strings, a privacy policy link, a data deletion path and explicit wording that emergency steps are quoted from the company manual and are not medical advice.

What remains is organisational rather than technical: Apple Developer Program organisation enrollment and Apple Business Manager (both need Axxiom's D-U-N-S number and are the slowest step), a published privacy policy URL, production configuration values, and a reviewer account. The full checklist, including the review notes to paste into App Store Connect, is in docs/apple-review.md.

15Things that will bite you

Every item here cost time to find. They are written down so they cost it once.

AreaWhat happensWhat to do
StreamingA request that fails to start can leave a stream that never yields, so the technician watches a spinner until the function times outNever swallow the error when starting the stream. This was a real bug; a failure now surfaces in about a second
CitationsThe model's own citation blocks do not reliably attach to quoted policy textVerified verbatim quotes are the primary evidence; model citations supplement them
Quote matchingQuotes fail to verify because of bullets, bold markers, table rows or a page break mid-sentenceEach quoted line is verified separately, with markdown stripped and the next page joined for the search
CachingCache hit rate collapses and cost multipliesAnything that changes bytes before the breakpoint invalidates the cache: a timestamp in the prompt, a new extraction tool version, a reordered document
EvaluationsLatency looks terrible at high concurrencyRun at two at a time. Four triggered rate-limit retries that showed up as 60-second first-token times
iOS testingA walkthrough fails at a random stepiOS shows a save-password sheet and a typing tutorial over the app, and the sign-in session survives between runs. The test dismisses all three
MonitoringTrace queries return nothingOrganisations created recently must use the version 2 observations endpoint; the legacy traces endpoint is gone
SecretsA token silently becomes invalidKeep a trailing newline in the environment file. A value appended to a line without one corrupts the token above it

Decisions worth revisiting later, but not now

  • Retrieval. The whole manual fits in the model's context, so there is no search step to get wrong. If the corpus grows past roughly half a million tokens, add retrieval then, and prove with the evaluation harness that accuracy did not drop.
  • Memory of the technician. Deliberately absent. A safety assistant should give everyone the same policy answer, and remembering personal details raises questions about records that are already sensitive.
  • Spanish. Would need its own test set. The assistant would answer in Spanish while citing the English policy.
  • Android. Not planned. If it arrives, the API and the event contract are unchanged; only the app is new.
